目标是准备技术面试：把机制讲清、把应用做出来、拿出证据、应对条件变化。既有课程的 Python、模型和张量基础直接复用。用户自报已经理解 attention 与位置编码；本路线不以继续推导 Transformer 为前置条件。

## 深度到哪里

| 主课必须会 | 可以借助文档完成 | 现阶段不作为前置要求 |
|---|---|---|
| 画出请求、数据、身份和状态的流向 | 记不住的 API 参数、Docker 命令、云控制台入口 | attention/反向传播/RoPE 的数学推导 |
| 完成小函数、接接口、部署和排错 | 框架初始化、通信和展示代码 | 从头训练大模型、实现向量索引算法 |
| 根据数据解释选型、效果、费用和故障 | 产品价格、模型能力和服务配额查询 | 多卡训练集群、复杂 K8s 运维 |
| 对未知项提出测量方法，不把猜测写成事实 | 一次新的 SDK 或数据库连接写法 | 背所有厂商的产品目录 |

必要原理放到问题出现时讲。例如：遇到首段输出慢，才补输入处理与生成、流式返回和 KV cache；检索找错材料，才补文本向量和相似度的直觉。保留 token 费用、容量和并发估算，这些不是模型数学推导。

## 连续项目

起点：虚构团队的一份设备借用说明。第一课的模型要根据它回答“最多借多久、到期谁处理”。随后加入设备报修、账号开通、历史版本和不同用户权限，再接工单查询和草稿保存。

业务只是让数据流具体可见。相同能力可以迁移到产品支持、企业知识库、文档助手和业务自动化。

## 课程安排

每课分成 2–3 段，每段操作约 20–30 分钟；讨论和排障另计。全线约 45–65 小时是初步安排，不是完成面试准备的保证。可按每周 6–8 小时进行，理解卡住时只修补那一段。

| 课 | 为什么接着学这一课 | 动手做什么 | 留下什么，面试能回答什么 |
|---|---|---|---|
| **01 · 一次模型请求，怎样才算成功** | 学过模型输入输出，现在要判断实际接口是否可用、结果是否可信 | 调用已有 DeepSeek/TokenHub；对比无材料与带材料；检查响应与用量；用明确标注的故障样本诊断 401/429/超时/截断 | 两次真实记录、一处结果判断小函数。说明连通、生成完成和事实正确为何不同 |
| **02 · 把模型能力变成 HTTP 服务** | Notebook 能运行，别的程序还不能直接使用 | 用 FastAPI 提供 `/health` 和 `/ask`；校验输入、密钥放后端；观察流式与非流式；用 curl 调用 | 可复现接口。讲清客户端、应用和模型商三层，健康检查能证明什么 |
| **03 · 第一台云服务器** | 要让本机之外的环境也运行同一服务 | 核价后创建/复用 CPU 主机；SSH、Docker、环境变量；先通过 SSH 隧道访问；重启再验证 | 云端运行记录和请求图。区分进程、容器、端口、云主机与模型计算位置 |
| **04 · 网络与访问边界** | 云端跑通后，要解释谁能访问、为什么有时访问不到 | 验证监听地址、安全组和系统防火墙；沿请求理解 DNS/TLS；应用认证；修改一条规则观察并恢复 | 一次实际网络排错。能分辨连接失败、认证失败与应用错误；数据库不直接暴露公网 |
| **05 · 资料怎样存、更新和恢复** | 每次手动粘贴材料容易过期，也无法留下业务状态 | 小规模 PostgreSQL 存元数据/工单；文件存储与对象存储各做一次；给文档来源和版本；备份后实际恢复 | 数据表、文件关系和恢复记录。说明数据库、原文件、搜索索引各负责什么 |
| **06 · 做出第一条 RAG 链路** | 资料变多，需要自动选择材料再交给模型 | 文档切分→真实文本向量→索引→检索→真实模型回答；展示命中片段和引用；先完成小数据量全链路 | 能从问题追到引用原文。区分手工塞材料与自动检索；不手推相似度公式 |
| **07 · 找错了，还是答错了** | 一个能回答的 RAG 还不知道好不好 | 固定小问题集，覆盖存在/缺失/过期/冲突；分别评检索和回答；只改切分、混合检索或重排中的一项 | 改前改后结果与保留问题。说明为什么一次演示成功不足以证明整体效果 |
| **08 · 同一套资料，不同人能看什么** | 检索有用后，错误的资料范围会带来错误和越权 | 两个测试身份；检索前/时按权限过滤；版本更新和删除后重建；测试文档夹带指令 | 权限和更新实验。解释提示词约束与程序授权为什么不能混用 |
| **09 · 从回答变成实际动作** | “已创建工单”这句话不等于数据库有记录 | 结构化结果校验；只读查询工具；验证参数后写工单草稿，检查实际记录；未批准不正式执行 | 工具调用记录。讲清模型提议、代码验证、业务执行三者职责 |
| **10 · 工作流与 Agent** | 多步骤任务会失败，也可能重复执行 | 先固定流程，再让模型有限选择下一步；保存状态、限制步数与用量；制造写入后响应丢失，恢复且不重复写 | 状态记录与对照。解释什么时候选固定流程，什么时候值得用 Agent |
| **11 · 用户只说失败了，怎样查** | 系统跨越多个组件，只有一条错误提示不够 | 用 request ID 串起应用、检索和模型记录；注入超时/服务错误；设置有限重试与等待、降级和告警 | 一次带证据的故障复盘。区分超时与未执行，避免无上限重试 |
| **12 · 为什么变慢，怎样花得更少** | 可用后才有必要优化 | 先用本地替身测应用并发，再做限量真实请求；区分首段、总耗时、排队；验证缓存更新和后台任务 | 小规模性能表、费用账。解释缓存可能返回旧答案，不能把一次耗时称为 p95 |
| **13 · 从一台机器到可恢复的架构** | 单实例是练习环境，生产还要考虑故障范围 | 画多实例/负载均衡/共享数据；本地双实例验证；云上限时做一项网络或恢复实验；测恢复耗时 | 架构图和实测边界。讲清单点、数据恢复、可用区以及自建与托管的取舍 |
| **14 · 模型与部署方式怎样选** | 效果或费用不合适时，需要比较不同改法 | 固定任务比较实际可用模型；对照 API 与本机小模型（选做）；判断补资料、改提示、换模型、微调 | 选型记录。解释质量、延迟、成本、隐私与维护；未做微调就不写成经历 |
| **15 · 系统设计面试** | 已做过组件，现在练在约束下组合 | 给用户量、文档量、权限、预算、响应目标；画请求与数据流，估容量；临时增加私网/故障/用户翻倍条件 | 一张能解释的图、资源账和备选方案。先明确需求，再作选择 |
| **16 · 项目深挖与模拟面试** | 跟做成功后，还要离开提示说清楚 | 从自己的记录讲一次错误与修正；60–90 秒解释，再承接 5–10 分钟追问；小函数/日志定位题 | 诚实的项目陈述。区分个人实现、助手提供代码、教学数据、实际运行与设计设想 |

01、02、实际第三课 RAG 和第四课评估已制作；当前入口为 [04-rag-evaluation/LESSON.md](04-rag-evaluation/LESSON.md)。第二课用户自报完成；基础云部署/网络按用户选择跳过，其他专题按需要制作。

媒介不固定：服务开发、云部署以普通 Python 项目、终端、配置和测试为主；只有需要探索数据或可视化时再考虑 Notebook。不以“全部做成 Jupyter”约束后续课程。

## 三个阶段检查

- **04 之后：** 本机和云端都能调用，能够沿请求路径排查一次访问故障。若 API 基础已经熟练，减少重复调用，不整课重学 JSON。
- **08 之后：** 有一套能展示来源、版本、权限和失败用例的 RAG；能区分检索问题与回答问题。
- **13 之后：** 有实际工具执行、恢复、测量和费用记录；能解释单实例实验与生产设计的差别。

不会为填满目录提前制作所有课件。每个阶段之后，以你的复述和一次条件变化题调整下一段；代码运行检查只证明程序运行。

## 云平台与工具选择

先用一个云练完整链路，默认腾讯云。学完后把概念映射到阿里云或 AWS：虚拟机、对象存储、VPC、安全组、身份权限、托管数据库、负载均衡、模型服务。迁移时核对差异，不再从头重做三个项目。

Python、FastAPI、Docker、PostgreSQL 和一个向量检索实现是候选工具；先看具体问题，再在制作对应课时定依赖。初版 RAG 不要求 LangChain，初版 Agent 用可读的小循环；有了完整链路后再比较框架、MCP 和低代码平台的适用边界。

面试准备保留少量真实沟通经历：解释技术选择、处理不同意见、承认并修正错误。你的售前和生态经验可以提供素材，课程时间主要投入云与 AI 工程能力。若目标 JD 额外要求算法笔试、K8s 或行业专长，再单列补充模块。
