# Kernel behind a custom lesson page

Checked against primary docs, GitHub, and the PyPI JSON API on 1 November 2026. The learner is one person on a Mac; nothing here assumes a public server. A browser page cannot speak ZeroMQ to a kernel. Something on the machine has to translate the page’s HTTP and WebSocket calls into the kernel protocol.

## What does each project do, and is it maintained as of 2026?

### Takeaway

The page library and the process that actually starts CPython are different pieces. Thebe (npm, January 2025) is the page-side library. Jupyter Server 2.21.1 (September 2026) is the maintained local bridge to a real kernel. `jupyter_client` 8.10.0 (August 2026) is the Python library that bridge uses; it is not something a static page can import. Kernel Gateway 3.0.1 (March 2024) is the older headless bridge and has had no release since then. Jupyverse 0.14.18 (October 2026) is the FastAPI server still shipping in 2026; it is another Jupyter server, not a lesson UI, and its experimental “POST this cell” API is not a raw code runner.

Repository README, which also splits the project into `thebe` (browser bundle that makes marked code cells editable and executable), `thebe-core` (lower-level server, session, notebook, and cell objects), `thebe-lite` (adds a JupyterLite server for WASM kernels), and `thebe-react`: [jupyter-book/thebe](https://github.com/jupyter-book/thebe).

### Inferences

- For this lesson, the 2026 piece that is still shipping and that can launch the existing CPython is Jupyter Server. Thebe is the ready-made page library, but its last release is January 2025, so pairing it with a 2026 server means living with an older client. Jupyverse is the actively released alternate server, not a replacement for the lesson page.
- Kernel Gateway’s websocket mode is the same idea as Jupyter Server’s kernel API, and since the 3.0 line it sits on Jupyter Server. As of November 2026 it is a frozen packaging of that idea, not the project receiving fixes.
- `jupyter_client` never becomes the page. A static page still needs Jupyter Server, Kernel Gateway, or Jupyverse (or a small bridge you would write yourself) in front of it.
- `thebe-lite` and JupyterLite run a WASM kernel in the browser. That path does not import `torch` or `tokenizers` from the uv virtualenv. The local-server path is the one that can.
- The Jupyverse execute-by-POST route is a collaboration feature tied to a notebook document and a cell index. It is not the documented way for a lesson page to send an arbitrary string of code.

### Gaps

- No GitHub commit dated 2026 was opened for `jupyter-book/thebe` beyond the existence of a pull request opened 16 June 2026. “Last meaningful commit” inside the source, as opposed to the January 2025 tag, was not checked line by line.
- Jupyverse 0.14.18’s kernel WebSocket was not compared request-by-request with Thebe’s `serverSettings`. Whether Thebe 0.9.3 can point at Jupyverse with only a base URL and a token was not verified.
- Jupyter Enterprise Gateway was not reviewed. It is a separate project from Kernel Gateway.

## Can the page show its own lesson, a code editor, and a Run button, while the kernel stays invisible?

### Takeaway

Yes. The kernel never has a window of its own. Thebe’s ordinary bundle keeps the surrounding lesson HTML and turns marked code blocks into its own editor plus Run and Restart buttons. A lower-level page can own the buttons. JupyterLab does not have to be the page. Kernel Gateway serves no notebook editor at all. A page that wants a completely foreign editor, such as an existing Monaco or CodeMirror already in the lesson, is past what the Thebe “drop in a script tag” docs cover; that page talks to the kernel protocol itself.

### Cited Findings

- Thebe’s own pages are ordinary HTML. The local-server example is a page of explanation plus Python cells, and the kernel provider is a Jupyter server started separately: [Thebe: using a local server](https://thebe.readthedocs.io/en/latest/_static/html_examples/local.html). Configuration lives in a `<script type="text/x-thebe-config">` block in the page: [Configure Thebe](https://thebe.readthedocs.io/en/latest/configure.html).
- On activation, elements with `data-executable="true"` “will be converted to code cells and control buttons are rendered by default.” Per-cell buttons are Run, Restart, and Restart All, and each can be turned off with `mountRunButton`, `mountRestartButton`, and `mountRestartAllButton`. A status widget is a `<div class="thebe-status" />` the page places itself: [User Interface](https://thebe.readthedocs.io/en/latest/ui.html).
- “Currently there can be only one kernel per page,” requested with `kernelOptions.kernelName`: [Configure Thebe](https://thebe.readthedocs.io/en/latest/configure.html).
- Published `thebe-core@0.5.0` wraps a JupyterLab session connection. `ThebeSession.restart()` calls `this.connection.kernel.restart()`, and the session object exposes `.kernel`: [thebe-core 0.5.0 session.ts on unpkg](https://app.unpkg.com/thebe-core@0.5.0/files/src/session.ts). The package README describes `thebe-core` as access to servers, sessions, notebooks, and cells rather than as a full IDE: [jupyter-book/thebe](https://github.com/jupyter-book/thebe).
- Kernel Gateway: “There are no provisions for editing notebooks through the Kernel Gateway.” The calling application is responsible for the UI: [Jupyter Kernel Gateway](https://jupyter-kernel-gateway.readthedocs.io/en/latest/). Its websocket mode is explicitly for “send[ing] code to kernels for interactive evaluation,” with Node and Python demos, not a built-in editor: [jupyter-websocket mode](https://jupyter-kernel-gateway.readthedocs.io/en/latest/websocket-mode.html).
- Jupyter Server is the backend those web applications use, not the lesson layout: [jupyter-server on PyPI](https://pypi.org/project/jupyter-server/). Visiting a token URL in the browser shows a page whose documented message is “A Jupyter Server is running,” which is the server’s own landing page, not JupyterLab: [Security in the Jupyter Server](https://jupyter-server.readthedocs.io/en/latest/operators/security.html).
- `KernelClient.execute` is a Python call over ZeroMQ. The documented client is not a browser script: [jupyter_client package](https://jupyter-client.readthedocs.io/en/stable/api/jupyter_client.html). The browser side of the same protocol is the WebSocket format Jupyter Server documents: [WebSocket kernel wire protocols](https://jupyter-server.readthedocs.io/en/latest/developers/websocket-protocols.html).

### Inferences

- The high-level Thebe script is the closest match to “lesson prose, a code box, and a Run button” without writing a client. The lesson author owns the HTML around the cells. Thebe owns the cell that appears where `data-executable` was.
- Kernel Gateway and Jupyter Server can both sit behind a page you design, including a Run button you wrote, because neither one is the editor. You then have to send `execute_request` and render the reply. Thebe-core is the existing library that already does that against Jupyter Server; using Jupyter Server’s WebSocket from scratch means implementing the framing in the protocol doc.
- “Invisible kernel” is the default. Nothing in these servers opens an editor window unless the command you launch is itself JupyterLab or the classic notebook app, or the student follows the server’s printed URL.

### Gaps

- No current Thebe document was found that shows a lesson-owned Monaco or CodeMirror instance whose buffer is sent as a bare string, with Thebe rendering only the output. The published session object exposes `.kernel`, but the docs that were opened still center on Thebe cells.
- Whether Jupyverse’s notebook and lab extras can be left uninstalled and still serve only the kernel API to a static page was not checked.

## Does the kernel keep variables between runs, the way a notebook does? How is a restart exposed?

### Takeaway

Yes, while the page keeps using the same kernel. A notebook kernel is a separate process whose computational state survives from one execution to the next, and restart is how that state is reset. Thebe has one kernel for the page, so separate Run clicks share it. Restart is a button in Thebe’s cell UI, a `restart()` call in `thebe-core`, and `POST /api/kernels/{kernel_id}/restart` on Jupyter Server. Kernel Gateway’s websocket mode claims the notebook server’s HTTP API, which includes that restart route; the gateway’s own swagger file was not opened to quote the path.

### Cited Findings

- “Code is run in a separate process called the Kernel.” “The kernel maintains the state of a notebook’s computations. You can reset this state by restarting the kernel.” [Running Code](https://jupyter-notebook.readthedocs.io/en/stable/examples/Notebook/Running%20Code.html).
- An `execute_request` asks the kernel to run code “in a namespace reserved to the user’s variables (and thus separate from the kernel’s own internal code and variables)”: [Messaging in Jupyter](https://jupyter-client.readthedocs.io/en/stable/messaging.html).
- The same messaging page says a kernel session id “should identify a particular kernel process” and “If a kernel is restarted, the kernel session ID should be regenerated.” A client that sees a new kernel session id “should assume that the kernel was restarted.” Restart is specified as its own control-channel operation; the recommendation is that a restart starts a new kernel process rather than wiping the parent server: [Messaging in Jupyter](https://jupyter-client.readthedocs.io/en/stable/messaging.html).
- Jupyter Server exposes that operation as `POST /api/kernels/{kernel_id}/restart`, status 200: [REST API](https://jupyter-server.readthedocs.io/en/latest/developers/rest-api.html).
- Thebe: one kernel per page: [Configure Thebe](https://thebe.readthedocs.io/en/latest/configure.html). Cell buttons include Restart and Restart All: [User Interface](https://thebe.readthedocs.io/en/latest/ui.html). `ThebeSession.restart()` awaits `connection.kernel.restart()` and emits status events for the restart: [thebe-core 0.5.0 session.ts](https://app.unpkg.com/thebe-core@0.5.0/files/src/session.ts).
- Kernel Gateway websocket mode “has the kernel gateway expose a superset of the HTTP API provided by the Jupyter Notebook server” plus the channels WebSocket: [jupyter-websocket mode](https://jupyter-kernel-gateway.readthedocs.io/en/latest/websocket-mode.html).
- `jupyter_client`’s `KernelManager` includes restart methods (`_async_restart_kernel`, `add_restart_callback`) on the object that manages the subprocess: [KernelManager](https://papyri.dev/project/jupyter_client/8.10.0/jupyter_client.manager$KernelManager/). A Python caller that keeps one `KernelClient` and calls `execute` again is talking to that same process: [KernelClient.execute](https://jupyter-client.readthedocs.io/en/stable/api/jupyter_client.html).

### Inferences

- Two Run clicks on one Thebe page share variables, imports, and defined functions, because they share one kernel process. A new kernel id, a shutdown followed by a new start, or a restart gives a fresh process and a fresh namespace.
- The lesson page has to show restart itself. JupyterLab’s Kernel menu is not on screen. Thebe can mount the button; a custom page calls the REST restart route or `session.restart()`.
- State is in the kernel process, not in the HTML. Closing the page does not, by itself, document a wipe. The notebook docs say an open notebook’s kernel stays active if the browser window is closed: [The Jupyter Notebook](https://jupyter-notebook.readthedocs.io/en/latest/notebook.html). The same process model applies when the client is a lesson page connected to that server. A server restart, or the kernel process exiting, does wipe it.

### Gaps

- Kernel Gateway’s `swagger.yaml` was not opened, so the restart path is inferred from “superset of the notebook HTTP API,” not quoted from the gateway’s own schema.
- No Thebe page was found that states, in those words, “a variable assigned in one cell is visible in the next.” That claim is the kernel’s, plus Thebe’s “one kernel per page.”
- Jupyverse’s restart route was not opened.

## What must be running on the student’s machine? Does the browser still need to open JupyterLab?

### Takeaway

One local server process, started from the uv environment that already has the packages, plus a way to open the lesson HTML. The browser does not need to open JupyterLab. Jupyter Server’s own `open_browser` default is false. Kernel Gateway has no notebook UI to open. The kernel that runs the code is whichever kernelspec that server process can see; the server has to be the uv environment’s Jupyter, or the kernelspec has to point at that environment’s Python. `ipykernel` has to be installed there. Thebe’s published local example still says `jupyter notebook` with `NotebookApp.*` flags, which is the older spelling.

### Cited Findings

- Thebe’s local example assumes a server already running on port 8888, started as `jupyter notebook --NotebookApp.token=thebe-test-secret --NotebookApp.allow_origin='http://127.0.0.1:8080'`, and the page is separate HTML: [local server example](https://thebe.readthedocs.io/en/latest/_static/html_examples/local.html). `kernelOptions.serverSettings` is where a page sets `baseUrl` and `token` when it is not using Binder; the commented example is `http://127.0.0.1:8888` and a token: [Configuration Reference](https://thebe.readthedocs.io/en/stable/config_reference.html). `kernelName` must exist in the environment Thebe launches against: [Configure Thebe](https://thebe.readthedocs.io/en/latest/configure.html).
- Kernel Gateway, after `pip install jupyter_kernel_gateway`, is started with `jupyter kernelgateway`. The default websocket command in the docs is `jupyter kernelgateway --KernelGatewayApp.api=kernel_gateway.jupyter_websocket --port=10100`, and it logs a URL such as `http://127.0.0.1:10100` with no notebook UI: [Getting started](https://jupyter-kernel-gateway.readthedocs.io/en/latest/getting-started.html). Default API is `kernel_gateway.jupyter_websocket`, default port 8888, default listen address `127.0.0.1`: [Configuration options](https://jupyter-kernel-gateway.readthedocs.io/en/stable/config-options.html). The homepage says it launches kernels “in its local process/filesystem space” using the same code as Jupyter Notebook: [Jupyter Kernel Gateway](https://jupyter-kernel-gateway.readthedocs.io/en/latest/).
- Jupyter Server is a separate package from the Lab frontend: [jupyter-server on PyPI](https://pypi.org/project/jupyter-server/). `ServerApp.open_browser` defaults to false: “Whether to open in a browser after starting.” The `no-browser` flag sets `ServerApp.open_browser` to false: [full config](https://jupyter-server.readthedocs.io/en/latest/other/full-config.html), [serverapp.py flags](https://github.com/jupyter-server/jupyter_server/blob/main/jupyter_server/serverapp.py). The security page shows what you see if you do open the printed URL: a Jupyter Server page, and the token URL, not a requirement to open JupyterLab: [Security in the Jupyter Server](https://jupyter-server.readthedocs.io/en/latest/operators/security.html).
- Token authentication is on by default. The token can be passed as `Authorization: token …` or as a `token` URL parameter. A generated token is printed at startup. `JUPYTER_TOKEN` or `JUPYTER_TOKEN_FILE` can set it. Empty token and empty password turns authentication off, which the docs say is not recommended: [Security in the Jupyter Server](https://jupyter-server.readthedocs.io/en/latest/operators/security.html), [identity.py](https://github.com/jupyter-server/jupyter_server/blob/main/jupyter_server/auth/identity.py). `ServerApp.token` is deprecated in 2.0 in favor of `IdentityProvider.token`: [full config](https://jupyter-server.readthedocs.io/en/latest/other/full-config.html).
- Kernel Gateway’s auth token is `KernelGatewayApp.auth_token`, default `''`, “Authorization token required for all requests,” environment variable `KG_AUTH_TOKEN`. Its default is empty, unlike Jupyter Server: [Configuration options](https://jupyter-kernel-gateway.readthedocs.io/en/stable/config-options.html).
- A kernel is a separate program. Jupyter Client starts it as a subprocess: [KernelManager](https://papyri.dev/project/jupyter_client/8.10.0/jupyter_client.manager$KernelManager/), [Making kernels for Jupyter](https://jupyter-client.readthedocs.io/en/stable/kernels.html). The gateway’s kernelspecs endpoint lists the specs visible to that process; the getting-started `curl` of `/api/kernelspecs` shows a `python3` default coming from the environment where the gateway is running: [Getting started](https://jupyter-kernel-gateway.readthedocs.io/en/latest/getting-started.html).
- Jupyverse is installed with pip, for example `pip install "jupyverse[jupyterlab,auth]"`, and its overview lists “your personal machine” as a use: [PyPI description](https://pypi.org/project/jupyverse/), [overview](https://jupyter-server.github.io/jupyverse/). That install line includes the JupyterLab extra. An install line without a frontend extra was not copied from a tutorial in this pass; the overview says the server can run “JupyterLab and other web clients.”

### Inferences

- A single acceptable command for the maintained server, from the uv environment, is a `jupyter server` launch with a fixed token and an allowed origin for the lesson page. The documented knobs are `IdentityProvider.token` (or `JUPYTER_TOKEN`) and `ServerApp.allow_origin`. `--no-browser` matches the default but makes the intent obvious. The student then opens the lesson HTML, not `/lab`.
- The Thebe docs’ `jupyter notebook --NotebookApp...` line is older spelling. Jupyter Server 2.x documents `ServerApp` and `IdentityProvider`. Whether notebook 7 still accepts `NotebookApp.allow_origin` as an alias was not verified. Following the Thebe snippet literally on a 2026 server may not set the origin or the token the page expects.
- `torch` and `tokenizers` are importable only if the kernel’s Python is that uv environment. Starting the server with that environment’s `jupyter`, and requesting `kernelName: "python3"`, is the setup the docs support. A server installed in a different Python would launch that other Python unless a kernelspec points back at the uv interpreter.
- The student does not open JupyterLab. They do need a terminal command left running, and they open the lesson page in a browser. If the command is `jupyter lab` or `jupyter notebook`, that app may still be what the flag is attached to; those apps’ 2026 `open_browser` defaults were not checked. `jupyter server` itself defaults to not opening a browser.

## What are the practical problems for a local lesson: ports, tokens, CORS, widget output versus plain text?

### Takeaway

The page and the kernel server are different origins unless you deliberately serve the HTML from the Jupyter process. Cross-origin pages need an allow-origin setting and the token. Jupyter Server’s CSRF rule accepts either a same-origin page or a token, so a lesson on another port can work if the token is sent. Kernel Gateway’s token defaults to empty and its allow-origin defaults to empty. Plain text and images travel as MIME bundles on the ordinary execute result; a live widget needs a widget front end that speaks the comm protocol. Thebe includes that for its own cells. A page that only prints `text/plain` will show `print` and `repr` and will not show a slider.

### Cited Findings

- Jupyter Server listen examples in the security docs are `http://localhost:8888` and `http://127.0.0.1:8888`: [Security in the Jupyter Server](https://jupyter-server.readthedocs.io/en/latest/operators/security.html). Kernel Gateway’s default port is 8888, default address `127.0.0.1`, and `port_retries` defaults to 50, “Number of ports to try if the specified port is not available”: [Configuration options](https://jupyter-kernel-gateway.readthedocs.io/en/stable/config-options.html). Troubleshooting says the server “listens on port 8888 by default”: [Troubleshooting](https://jupyter-kernel-gateway.readthedocs.io/en/stable/troubleshooting.html).
- `ServerApp.allow_origin` defaults to `''`. `'*'` allows any origin. It takes precedence over `allow_origin_pat`. A regex form echoes the request origin when it matches: [full config](https://jupyter-server.readthedocs.io/en/latest/other/full-config.html), [serverapp.py](https://github.com/jupyter-server/jupyter_server/blob/main/jupyter_server/serverapp.py). Kernel Gateway has the same idea as `KernelGatewayApp.allow_origin`, default `''`, environment variable `KG_ALLOW_ORIGIN`: [Configuration options](https://jupyter-kernel-gateway.readthedocs.io/en/stable/config-options.html). Thebe’s local example sets the origin to the page’s origin, `http://127.0.0.1:8080`: [local server example](https://thebe.readthedocs.io/en/latest/_static/html_examples/local.html).
- CSRF: `ServerApp.disable_check_xsrf` defaults to false. The server requires API requests to “either originate from pages served by this server (validated with XSRF cookie and token), or authenticate with a token.” The docs reserve turning all of this off for anonymous compute, and they say to do that only with “full knowledge of what that implies”: [full config](https://jupyter-server.readthedocs.io/en/latest/other/full-config.html).
- Token in the page is a Thebe `serverSettings.token` field: [Configuration Reference](https://thebe.readthedocs.io/en/stable/config_reference.html). Jupyter Server treats that secret as the credential for arbitrary code execution; the security page says access to the server “means access to running arbitrary code,” and execute permission on `kernels` “generally means arbitrary code execution”: [Security in the Jupyter Server](https://jupyter-server.readthedocs.io/en/latest/operators/security.html). Kernel Gateway’s default `auth_token` is empty: [Configuration options](https://jupyter-kernel-gateway.readthedocs.io/en/stable/config-options.html). Its Docker example binds `0.0.0.0`, which is not the localhost default: [Getting started](https://jupyter-kernel-gateway.readthedocs.io/en/latest/getting-started.html).
- Execute results “can have multiple simultaneous formats.” “A plain text representation should always be provided in the `text/plain` mime-type.” “Frontends should ignore mime-types they do not understand”: [Messaging in Jupyter](https://jupyter-client.readthedocs.io/en/stable/messaging.html). The same page documents `display_data` and `execute_result` as those MIME bundles, and separately documents `comm_msg` for side channels.
- ipywidgets’ embedding document is about serializing widget state into static HTML (`application/vnd.jupyter.widget-state+json` plus `@jupyter-widgets/html-manager`). That is a snapshot, and the Python example even says you can open the exported file from `file://`: [Embedding Jupyter Widgets](https://ipywidgets.readthedocs.io/en/latest/embedding.html). Thebe’s live examples are a different thing: the docs list ipywidgets, bqplot, ipyleaflet, ipympl, plotly, and matplotlib-plus-interact examples against a kernel: [Thebe](https://thebe.readthedocs.io/en/latest/). `thebe-core` 0.5.0 constructs a `ThebeManager` with the kernel and a rendermime registry, which is the live connection rather than a frozen embed: [session.ts](https://app.unpkg.com/thebe-core@0.5.0/files/src/session.ts).
- `execute_request` includes `allow_stdin`. If it is false, “the kernel should not send” `input_request` messages. Frontends that do not support stdin are called out in the spec: [Messaging in Jupyter](https://jupyter-client.readthedocs.io/en/stable/messaging.html).

### Inferences

- Two local processes both wanting port 8888 will collide. Kernel Gateway will walk up to 50 ports, so a page hardcoded to 8888 can miss a gateway that quietly moved. Pin the port and make the page use that same port.
- Serving the lesson from `file://` does not match the origin in Thebe’s local example (`http://127.0.0.1:8080`). A tiny local static server on a fixed port, plus `allow_origin` set to that origin, is the setup the Thebe page actually documents. Putting the HTML on the Jupyter origin avoids the cross-origin case the CSRF text describes; how to mount a custom lesson as a static file inside Jupyter Server was not checked.
- The token will sit in the lesson page or in its config if the page sends it. On one Mac, binding to `127.0.0.1` keeps that credential off other machines. An empty Kernel Gateway token is the documented default and means the localhost port is unauthenticated code execution. For a lesson, set `KG_AUTH_TOKEN` or `IdentityProvider.token` to a fixed value the page knows, and do not use the Docker sample’s `0.0.0.0`.
- `print(...)` and an expression result can be shown from `text/plain` without ipywidgets. A matplotlib PNG can be shown only if the page understands `image/png` in the MIME bundle; a frontend is allowed to ignore types it does not implement, so a text-only renderer will drop the figure. A live slider or ipympl figure needs the comm channel and a widget manager. Thebe’s examples cover that case. A hand-rolled Run button that only reads `text/plain` does not.
- `input()` needs a stdin implementation. A lesson page that never answers `input_request` should send `allow_stdin: false` or avoid `input()` in the exercises.

### Gaps

- A same-origin layout (lesson HTML served by Jupyter Server at `/files/...` or a custom static handler) was not tested, so it is not claimed as a working CORS workaround.
- WebSocket-specific origin checks, beyond the HTTP `allow_origin` setting, were not read in the server source.
- Thebe’s behavior when `text/plain` and `image/png` arrive together was not executed against this machine’s `torch` environment. The protocol and Thebe’s example list are the evidence.
- Jupyverse CORS, token, and widget behavior were not compared with Jupyter Server’s.
